# Эксплуатация: запуск, режимы, проверка

Порядок запуска терминала на чистой машине и то, что проверено запуском
2026-09-03 (TRM-01). Всё, что ниже, воспроизведено на этой машине; чего
проверить не удалось — помечено отдельно.

Терминала **нет ни на одном сервере** — ни на тестовом VPS, ни в проде.
Единственная среда — рабочая машина разработчика; тестового VPS не будет
(решение Р-006).

## Запуск

```bash
git clone <адрес репозитория> terminal
cd terminal
docker compose up --build -d   # первый запуск долгий: собирается Rust (~5 мин)
```

Открывать: **http://localhost:8888**. Наружу торчит только контейнер `terminal`
(nginx); он же проксирует REST и WS на внутренний `gateway`. Порт 8888 — потому
что диапазон 8080–8282 на рабочей машине занят WinNAT.

Поднимаются три контейнера: `exchange-postgres`, `exchange-gateway`,
`exchange-terminal`. Локального Rust/Node не нужно — весь тулчейн в Docker
(ADR-004).

## Что обязательно, а что опционально

| Что | Обязательно? | Без него |
|---|---|---|
| Docker + docker compose | да | ничего не поднимется |
| Выход в интернет | **да** | нет цен: свечи, стакан и лента идут с Binance напрямую |
| `postgres` из compose | нет в standalone, **да** при включённом SSO | без `DATABASE_URL` gateway уходит в `MemoryStore`: состояние и журнал счёта живут в памяти процесса до рестарта. При SSO нужен identity-маппинг `(tenant, sub)`, которого в памяти нет |
| Кабинет платформы (:3002) | нет в дефолте, да при `SSO_DISABLED=0` | при включённом SSO торговые ручки отдают 401 |
| CMS платформы (:3001) | нет | бренд не грузится, рисуется палитра платформы по умолчанию |
| `.env` | нет | берутся дефолты из `docker-compose.yml` (годятся только для разработки) |

Ключей и токенов для рыночных данных не нужно **ни одного**: используются
публичные эндпоинты Binance.

## Два режима запуска — главная развилка

**Дефолт репозитория — standalone** (решение штаба 2026-09-03): терминал
поднимается сам по себе, без кабинета и без CMS. `docker compose up -d` — и
торговля работает на счёте по умолчанию (`DEFAULT_USER = UserId(1)`), баланс
$10k, консоль чистая.

Режим задаётся **тремя** переменными, и они должны быть согласованы:

| | standalone (дефолт) | интеграция с платформой |
|---|---|---|
| `SSO_DISABLED` | `1` | `0` |
| `CABINET_ORIGIN` | пусто | origin кабинета |
| `BRAND_URL` | пусто | brand-эндпоинт CMS |

Почему все три, а не одна: `SSO_DISABLED` управляет **бэкендом**, а
`CABINET_ORIGIN` — **фронтом**. Непустой `CABINET_ORIGIN` включает у фронта
embedded-режим, в котором без handoff-токена торговые ручки не дёргаются вовсе
(`api.js: tradingBlocked`) — даже если gateway стоит в standalone и ответил бы.
Непустой `BRAND_URL` без живой CMS даёт ошибку в консоли на каждой загрузке.

```bash
# интеграция: кабинет и CMS подняты на хосте
SSO_DISABLED=0 CABINET_ORIGIN=http://localhost:3002 BRAND_URL=http://localhost:3001/v1/cms/brand docker compose up -d
```

Если включить SSO, а кабинета нет: график, стакан, лента и watchlist работают на
живых данных, `/account` и `/deals` отдают **401 `missing session`**, а терминал
показывает прочерки и явное `NO CABINET SESSION — TRADING UNAVAILABLE`. Раньше в
этом состоянии рисовался **BALANCE $0** — отказ, неотличимый от настоящего нуля
(BUG-011). Оба состояния проверены headless 2026-09-03.

⚠️ При включённом SSO **база обязательна**: identity-маппинг `(tenant, sub)` без
БД не реализован, `POST /v1/session` без БД вернёт 503.

## Поведение без `DATABASE_URL`

Проверено отдельным запуском образа `terminal-gateway` без переменной
(2026-09-03), работающий стек при этом не трогали:

```
[gateway] хранилище: нет (DATABASE_URL не задан) — состояние живёт только в памяти
```

Счёт отвечает, сделка открывается, маржа считается — теряется только
durability: рестарт обнуляет счета до стартового баланса.

⚠️ **Интерфейс об этом не сообщает.** В режиме `MemoryStore` терминал выглядит
ровно как с настоящим хранилищем: те же цифры, никакой пометки. После рестарта
человек увидит стартовый баланс и не отличит «состояние потеряно» от «я ничего
не наторговал» — тот же класс, что BUG-011, только в другую сторону. Признак
режима есть **только в логе gateway**, до пользователя он не доходит. Не
исправлено; учитывать при любой демонстрации на памяти. На `MemoryStore` идут
тесты — и путь записи, включая журнал счёта, в них **выполняется**: прежняя
заглушка `NoopStore` не делала ничего, и проверять на ней было нечего (TRM-13). С `DATABASE_URL` (дефолт compose) в логе `[gateway] хранилище: PostgreSQL`,
и `restore_state` поднимает счета из БД до приёма запросов; если БД не отвечает,
gateway не стартует — работать на неизвестном состоянии счетов нельзя.

## Переменные окружения

Задаются в `.env` (в git не попадает, шаблон — `.env.example`) или в окружении
`docker compose`.

| Переменная | Дефолт | Смысл |
|---|---|---|
| `POSTGRES_USER` / `_PASSWORD` / `_DB` | `platform` | на сервере пароль обязательно сменить |
| `SSO_DISABLED` | `1` (standalone) | `0` — торговые ручки требуют bearer-сессию по handoff-JWT |
| `CABINET_URL` | `http://host.docker.internal:3002` | откуда gateway берёт JWKS: `{CABINET_URL}/api/sso/jwks`. Пусто → SSO выключен |
| `DEMO_START_BALANCE_CENTS` | compose: `1000000` ($10k) | стартовый баланс демо-счёта. **Дефолт в коде другой — `10_000_000` ($100k)**: он действует, если переменную не передали (напр. при запуске образа руками) |
| `TENANT_INSTRUMENTS` | пусто | allow-list инструментов по сайтам, `site:1,2;other:3`. **Временный источник** вместо CMS (ключа контура нет). Пусто → в тенантном режиме торговля закрыта |
| `FRAME_ANCESTORS` | `*` | кто может встраивать терминал в iframe (CSP). В проде — список доменов сайтов |
| `BRAND_URL` | пусто | публичный brand-эндпоинт CMS. URL **для браузера**, не для контейнера. Пусто → бренд не грузим |
| `CABINET_ORIGIN` | пусто | origin кабинета-родителя для postMessage/SSO. Непустое значение переводит **фронт** в embedded-режим |

`BRAND_URL` и `CABINET_ORIGIN` подставляются в `config.js` через `envsubst` при
старте контейнера (`docker-entrypoint.d/40-terminal-config.sh`). Секретов в
`config.js` нет и быть не должно: файл отдаётся браузеру целиком.

## Как проверить, что всё живое

```bash
curl -s localhost:8888/health                      # см. поля ниже
curl -s localhost:8888/instruments | head -c 200   # last/bid/ask не null
curl -s 'localhost:8888/candles/1?tf=60&limit=3'   # свежие свечи
curl -s 'localhost:8888/depth/1?limit=5'           # стакан
docker logs exchange-gateway | tail -5             # [feed] Binance подключён (30 пар)
```

Живая лента (WS) — без клиента, руками:

```bash
timeout 10 curl -sN --http1.1 -H "Connection: Upgrade" -H "Upgrade: websocket" \
  -H "Sec-WebSocket-Key: dGhlIHNhbXBsZSBub25jZQ==" -H "Sec-WebSocket-Version: 13" \
  localhost:8888/stream | tr -c '[:print:]\n' '\n' | grep -a trade
```

**Данные реально с Binance, симуляции нет** — проверено 2026-09-03 на всех
четырёх путях: REST-свечи, REST-стакан, WS `@ticker`, WS `@aggTrade`. В коде
(`backend/gateway/src/feed.rs`) нет ни генератора, ни фикстур: только
`api.binance.com` и `stream.binance.com`. Цены сходятся с публичным Binance,
стакан меняется между двумя соседними запросами.

Поля `/health`:

| Поле | Смысл |
|---|---|
| `status` | сервис отвечает |
| `storage` / `durable` | режим хранилища: `postgres`/`true` или `memory`/`false` |
| `sso` | требуется ли сессия на торговых ручках |
| `feed_fresh` / `feed_age_secs` | возраст последнего **принятого** сообщения Binance (`null` — не было ни одного). Состояние сокета сознательно не отдаётся: открытое соединение без данных — молчащий фид |
| `priced_instruments` | по скольким парам есть живая цена |

Индикатор в шапке терминала горит по тому же признаку — по приходу данных, а не
по открытому соединению с gateway.

## Тесты и проверки

```bash
bash scripts/test.sh          # тесты Rust-workspace в Docker (rust:slim)
```

Кэш сборки лежит в томах `terminal-target` / `terminal-registry` (переименованы
из `platform-*` 2026-09-03; старые тома не удалены, решение по ним за владельцем).
Первый прогон после переименования собирает всё заново.

Прогон 2026-10-06: **121 тест Rust, все зелёные** (broker 30 + 17, gateway/lib 63,
gateway/api 7, persistence 4), clippy `-D warnings` чист.
Плюс **34 теста фронтенда** (индикаторы, см. ниже).

Мутационный прогон allow-list по символам (ADR-026), 2026-10-06 — пять мутаций
красят разные тесты, то есть набор проверяет разные вещи, а не одну пять раз:

| Мутация | Покраснело |
|---|---|
| неизвестный символ выбрасывается молча | 2 |
| индекс не знает канонического `BTCUSD` | 9 |
| fail-open: нет списка — разрешаем | 3 |
| нормализация не приводит регистр | 1 |
| «неизвестный символ» и «источника нет» слиты в один код | 1 |

Тесты фронтенда (TRM-05): **34 теста индикаторов** + **15 тестов виджета
watchlist**.

```bash
cd apps/terminal && npm ci     # только инструменты разработки, в поставку не идут
node --test apps/terminal/tests/*.test.js
```

Два харнесса, и выбор между ними не стилистический:

| Харнесс | Для чего | Чем даёт окружение |
|---|---|---|
| `tests/helpers/load-module.js` | чистые функции (индикаторы) | `vm`-песочница с фиктивным `window`, ноль зависимостей |
| `tests/helpers/load-widget.js` | виджеты `mount(root, ctx)` | jsdom: настоящий DOM, `localStorage`, события |

Виджет строит свой DOM, вешает слушатели и пишет в `localStorage` — подделать это
заглушкой нельзя, не превратив тест в проверку заглушки. jsdom живёт **только в
`devDependencies`** (решение владельца Р-020: «Разрешаем только для разработки»),
в образ не попадает: `apps/terminal/Dockerfile` копирует `public/` и npm не зовёт.
Позиция «ноль зависимостей в рантайме» цела.

⚠️ Объекты из песочницы и из jsdom принадлежат **другому realm**:
`deepStrictEqual` падает на прототипе при полностью совпадающем содержимом.
Сравнивать поэлементно.

⚠️ Каждый тест виджета обязан закрывать окно через `t.after`, а не в конце тела.
Иначе упавший assert оставляет таймер виджета живым, и **прогон виснет вместо
того, чтобы покраснеть**. Поймано мутацией «destroy не снимает таймер»: зависание
списывают на «что-то долго», красный тест — чинят.

Мутационный прогон виджета, 2026-10-06 — 8 мутаций, 7 красят тесты, каждая свой:

| Мутация | Покраснело |
|---|---|
| отказ источника превращается в пустой список | «источник вернул null» |
| отсутствующая котировка рисуется нулём | «прочерк, а не ноль» |
| строки пересоздаются на каждом обновлении | «переиспользует элементы строк» |
| `destroy` не снимает таймер | «destroy останавливает автообновление» |
| `columns()` отдаёт внутренний объект | «columns() отдаёт копию» |
| избранное не всплывает наверх | «избранное поднимается наверх» |
| избранное не пишется в `localStorage` | «избранное поднимается наверх» |
| `bid ?? -Infinity` → `bid ?? 0` | **никого, и это правильно** |

Последняя мутация неотличима по построению: цены неотрицательны, поэтому ноль и
минус бесконечность дают один и тот же порядок. Записано прямо в тесте, чтобы
никто не «дозакрывал» её ради полноты.

Эталонные значения посчитаны независимо от кода (отдельным скриптом по учебным
определениям). Ожидания, снятые с реализации, закрепили бы её ошибку.

**Мутационная проверка** — не разовая процедура, а способ проверять тесты.
Копируем `backend/` в сторону, возвращаем в копию исходный дефект, гоняем тесты:
покраснели ожидаемые — набор что-то проверяет; остались зелёными — не проверяет
(так вскрылся BUG-013). Рабочее дерево при этом не трогается.

**Как проверять отказ фида, не ломая процесс.** Поднять gateway с недоступной
биржей — ломается ровно путь данных, а не сервис:

```bash
docker run --rm -e SSO_DISABLED=1 -p 18082:8080 \
  --add-host api.binance.com:127.0.0.1 --add-host stream.binance.com:127.0.0.1 \
  terminal-gateway:latest
curl -s localhost:18082/health   # feed_fresh:false, feed_age_secs:null, priced_instruments:0
curl -s localhost:18082/candles/1  # 503 candles unavailable
curl -s localhost:18082/stats/1    # change: null во всех таймфреймах, не 0.00%
```

`docker kill` для этого не годится: он проверил бы политику перезапуска, а не фид.

Ручная проверка обоих режимов (пока автотестов фронта нет — это регресс-тест
BUG-011):

| Режим | Метрики | Предупреждение | Нижние панели |
|---|---|---|---|
| standalone (дефолт) | реальный баланс | скрыто | `No open positions` |
| `SSO_DISABLED=0`, кабинета нет | `—` | `NO CABINET SESSION — TRADING UNAVAILABLE` | `No cabinet session — trading unavailable` |

В обоих режимах консоль обязана быть пустой. Метрика CREDIT показывает `—` всегда:
источника данных у неё нет (см. BUG-011).

Отдельно — отказ рыночных данных. Воспроизводится в headless без остановки стека:
перехватить `**/candles/**`, `**/depth/**`, `**/stats/**` и отдать `503`
(`page.route(...).fulfill`). Ожидаемое поведение, проверено 2026-09-03:

- в шапке появляется `MARKET DATA UNAVAILABLE: CANDLES, DEPTH, STATS`;
- **график не стирается** — легенда продолжает показывать прежние цены; стакан
  оставляет прежние уровни. Пустой график читался бы как «рынка нет»;
- `change: null` в ответе `/stats` рисуется как `—`, а не как `0.00%`.

Фронтенд проверять **headless-браузером до слова «готово»** (принцип №20,
образ `mcr.microsoft.com/playwright`): рендер + консоль без ошибок. Так были
пойманы BUG-005/006/007. Контейнер удобно цеплять к сети стека:

```bash
docker run --rm --network terminal_default -v "<папка со скриптом>:/out" \
  -e URL=http://terminal/ mcr.microsoft.com/playwright:v1.49.0-noble \
  sh -c 'npm i playwright@1.49.0 --silent && node /out/check.js'
```

⚠️ В образе playwright лежат **браузеры, но не npm-пакет** `playwright` — его
нужно ставить в том же запуске.

## Модель ведения позиций (ADR-025)

Счёт работает по модели `hedging` (встречная сделка открывает вторую позицию) или
`netting` (сворачивает существующую). Модель отдаётся в `GET /account` полем `model`
и показана в шапке терминала — она меняет смысл каждой встречной сделки.

Схема БД мигрирует сама: `ALTER TABLE accounts ADD COLUMN IF NOT EXISTS model` в
`init()`. Существующие счета поднимаются как `hedging`. Проверить на живом стеке:

```bash
curl -s localhost:8888/account   # "model":"hedging"
```

Выбор модели из конфига тенанта пока не подключён (ждёт ключа к CMS), сменить её
можно только программно — `Broker::adopt_model`, и только на счёте без открытых
позиций.

## Инварианты денег (красная линия №5)

Проверяются **над слепком счёта**, поэтому работают одинаково с БД и без неё.
Зовутся в трёх местах: перед каждой записью счёта, в фоновом мониторе (триггеры
SL/TP и лимитных ордеров меняют счёт так же, как ручные операции) и на старте
после загрузки из хранилища.

| Ситуация | Что делает терминал |
|---|---|
| Операция сделала бы счёт неверным | `422 invariant_violated`, счёт откачен, изменение не зафиксировано |
| В хранилище уже неверно (нашли на старте) | **карантин счёта**: `423 account_quarantined` на мутации, чтение работает, сервис стартует |
| Триггер SL/TP привёл к нарушению | счёт в карантин, состояние **не записывается** |

Стоп сервиса не применяется нигде: одна испорченная строка не должна лишать
обслуживания всех. Молчаливой починки нет — испорченное сохраняется как есть,
иначе уничтожается улика. В логе нарушения печатаются с префиксом
`ИНВАРИАНТ НАРУШЕН`.

Вывести счёт из карантина можно только перезапуском после ручного разбора: это
намеренно, автоматического возврата нет.

## Allow-list инструментов (ADR-023 Т3, ADR-026)

Регуляторное требование: сайту нельзя торговать тем, чего его юрисдикция не
разрешает. Устройство:

- **Контракт — символы, не числовые id** (ADR-026, решение штаба Р-024). CMS
  отдаёт `instruments` плоским массивом строк (`BTCUSD`); терминал сопоставляет
  символ своему внутреннему id у себя на границе. Числовые id живут в `DEFS` и
  наружу не выходят: перенумерация внутри терминала иначе молча изменила бы,
  кому что разрешено торговать.
- **Неизвестный символ — отказ, а не пропуск**, и отказ на весь список сайта:
  молча выбросить разрешённое значит тихо сузить права.
- **Граница — путь открытия позиции**, а не витрина: `POST /deals` и
  `POST /pending` проверяют инструмент против списка сайта. Спрятать инструмент
  из списка недостаточно — торговать им прямым запросом всё равно можно.
- **Сайт берётся из сессии**, то есть из провалидированного handoff-токена.
  `?site=` из браузера подставит кто угодно, поэтому на нём граница не стоит.
- **Закрытие позиции и отмена ордера не ограничиваются.** Список ограничивает
  набор разрешённого, а закрытие позицию сокращает: запретив выход, мы заперли бы
  человека в том, что ему больше не разрешено держать.
- **Fail-closed** (КОНТРАКТЫ §4б): нет конфига сайта — торговли нет. Отказ
  инфраструктуры не должен превращаться в разрешение.
- **Standalone** (без `?site=`, SSO выключен): сайта нет, юрисдикции нет,
  доступен весь список.
- `GET /instruments?site=` фильтрует витрину — это удобство, не защита; пустой
  список инструментов не отдаётся никогда.

Коды отказа (все закрывают торговлю, но чинятся по-разному):

| Код | Что значит |
|---|---|
| `403 instrument_not_allowed` | список говорит «нет», окончательно |
| `403 no_instruments_allowed` | сайту не разрешено ничего (витрина) |
| `503 tenant_instruments_unavailable` | списка нет: CMS молчит/отказала/сайта нет |
| `503 tenant_instruments_unreadable` | список получен, но в нём неизвестные символы |

### Источник списка

Выбирается при старте, порядок объявляется строкой в лог:

1. **CMS**, если заданы **обе** переменные — `CMS_BASE_URL` и `CMS_API_KEY`:
   `GET {CMS_BASE_URL}/cms/sites/{slug}` под `X-API-Key`, сервер-сервер. Ключ в
   браузер не уходит. Читается **живым на каждую проверку**, без кеша (Р-030).
2. `TENANT_INSTRUMENTS` символами (`site:BTCUSD,ETHUSD;other:XRPUSD`) — разработка
   и офлайн.
3. Ничего — fail-closed.

Задана ровно одна из двух переменных CMS → источник CMS **не используется**, и в
лог уходит строка об этом. Наполовину сконфигурированный источник не должен
выглядеть как отсутствующий.

Проверить руками (контур поднят, ключ CMS — из окружения контура, не из репозитория):

```bash
# против живой CMS контура
CMS_BASE_URL=http://host.docker.internal:3101/v1 CMS_API_KEY=… \
  SSO_DISABLED=0 CABINET_URL=http://host.docker.internal:3102 docker compose up -d
curl -s 'localhost:8888/instruments?site=apex-ru'    # 403 no_instruments_allowed, пока список в CMS пуст

# против статического источника символами
TENANT_INSTRUMENTS='apex-ru:BTCUSD,ETH-USDT' SSO_DISABLED=0 docker compose up -d
curl -s 'localhost:8888/instruments?site=apex-ru'    # только BTC и ETH
curl -s 'localhost:8888/instruments?site=unknown'    # 503, не пустой список

# неизвестный символ в списке закрывает список целиком
TENANT_INSTRUMENTS='apex-ru:BTCUSD,XAUUSD' SSO_DISABLED=0 docker compose up -d
curl -s 'localhost:8888/instruments?site=apex-ru'    # 503 tenant_instruments_unreadable
```

## Живой прогон SSO — выполнен 2026-10-06 (TRM-04)

Контракт `sso-pack` был написан с двух сторон и **ни разу не прогонялся целиком**.
Прогнан на локальном контуре: кабинет `:3102`, CMS `:3101`, терминал `:8888`,
тенант `apex-ru`. Сессия кабинета заводилась через его же форму регистрации;
кабинет не правился.

Что проверено на **настоящем токене настоящего кабинета**:

| Пункт чеклиста | Как проверено | Результат |
|---|---|---|
| подпись по JWKS | `POST /v1/session` с живым токеном | `200`, сессия выдана |
| только `RS256` | заголовок подменён на `HS256` | `401` |
| подпись при подмене payload | `iss` переписан на `evil-auth` | `401`, в логе «подпись не сошлась» |
| `iss` | терминал пересобран с чужим ожидаемым `iss` | `401`, в логе «чужой iss» |
| `aud` | то же с чужим ожидаемым `aud` | `401`, в логе «чужой aud» |
| `exp` | — | закрыт юнит-тестом `validate_rejects_expired` |
| one-shot `jti` | тот же токен предъявлен дважды | второй раз `401 token already used` |
| `jti` не гасится при неудаче | токен предъявлен на чужой `site`, затем на свой | `403`, затем `200` |
| `tenant == site` | `site=other-site` | `403 tenant does not match site` |
| TTL сессии ≤ 15 мин | `expires_in` + замер | `900`; на `t+14:30` — `200`, на `t+15:30` — `401` |
| тихий ре-handoff | новый токен после истечения | `200`, торговля продолжилась |

**Как закрыт пункт `iss`/`aud`, который юнит-тестом закрыть нельзя.** Подделать
токен с чужим `iss` нечем: подпись проверяется раньше claims, и подменённый
payload падает на подписи — что прогон и показал отдельной строкой. Поэтому
инвертировалось **ожидание**, а не токен: терминал собран с чужим ожидаемым
`iss`, и настоящий токен кабинета — та же подпись, тот же JWKS — был отвергнут
именно по `iss`. Тот же токен в неизменённом терминале прошёл. Наблюдаемое
различие даёт именно наш барьер, а не чужой слой.

Это стало возможно только после BUG-014: до него все отказы схлопывались в один
`401` без следа в логе, и отличить «не сошлась подпись» от «токен не нам» было
нечем ни снаружи, ни изнутри.

**Три переменные задаются вместе** (иначе получится конфигурация, выглядящая
исправленной): `SSO_DISABLED=0` и `CABINET_URL` — бэкенду, `CABINET_ORIGIN` —
фронту. Для контура: `CABINET_URL=http://host.docker.internal:3102`,
`CABINET_ORIGIN=http://localhost:3102`.

Чего прогон **не** покрыл: `postMessage`-часть (`sso.token`,
`token.refresh.request`, `sso.logout`) — она живёт в браузере внутри iframe
кабинета, и проверялась только бэкендовая половина обмена.

## CD — `.github/workflows/deploy.yml`

Запускается **вручную** (workflow_dispatch). Нужны секреты `DEPLOY_HOST`,
`DEPLOY_USER`, `DEPLOY_SSH_KEY`, опционально `DEPLOY_PATH`. Пока их нет,
workflow останавливается с понятным сообщением. **Ни разу не выполнялся:**
сервера у терминала нет ни одного. Инфраструктурный контур — зона команды
`deploy`; адреса машин в этом репозитории не держим, он публичный.

## Грабли

- **Конфликт имён контейнеров.** `container_name` в compose фиксированные
  (`exchange-*`). Если на машине остался стек другого проекта с теми же именами
  (например, допивотный `platform` из соседней папки), `docker compose up` падает
  на `Conflict. The container name "/exchange-postgres" is already in use`.
  Смотреть, чей контейнер, **до** удаления:
  `docker inspect exchange-postgres --format '{{index .Config.Labels "com.docker.compose.project.working_dir"}}'`.
- **`docker compose down --remove-orphans` при рестарте после смены compose** —
  иначе прилипают контейнеры снятых сервисов.
- **Новый REST-путь → добавить в регекс прокси** `apps/terminal/nginx.conf`
  (BUG-004). Граница `(/|$)` обязательна, иначе статика с тем же префиксом
  (`stats.js`) уедет в прокси (BUG-007).
- **Состояние живёт в томе `terminal_pgdata` на конкретной машине.** Между
  машинами переносится код, а не данные.
- **Режим задаётся тремя переменными, а не одной.** Включить `SSO_DISABLED=0`,
  забыв `CABINET_ORIGIN`, — рабочая на вид конфигурация, в которой фронт вообще
  не ходит в торговые ручки. И наоборот: задать `CABINET_ORIGIN` при
  `SSO_DISABLED=1` — торговля отключится на фронте, хотя бэкенд её разрешает.
