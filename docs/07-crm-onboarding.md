# CRM / бэк-офис — инструкция для сессии, которая это пишет

Ты начинаешь **CRM (бэк-офис)** для платформы. Работаешь в том же репозитории и по тем же правилам,
что и основная сессия. Этот файл — твой брифинг. Прочитай его целиком, потом документы из раздела
«Сначала прочитай», и только затем пиши код.

## Сначала прочитай (обязательно)

1. `docs/00-principles/development-principles.md` — принципы разработки (`accepted`, не пожелания).
2. `docs/STATUS.md` — где сейчас проект, структура, что уже сделано.
3. `docs/README.md` — карта документации и всех ADR.
4. `docs/01-architecture/decisions/ADR-016..021` — деньги/персистентность, структура репозитория
   (`apps/`+`backend/`), аутентификация (сессии, Argon2id), поддомены, Passkey, OAuth. CRM опирается
   на всё это.
5. `docs/06-operations.md` — как запускать (Docker, домен meriom.com, mkcert).

## Что такое CRM здесь

Внутренний бэк-офис оператора брокера: видеть всех клиентов и их счета, править данные, **двигать
деньги** (пополнить/списать/скорректировать), **блокировать** счета, вести историю действий. Это
нормальные операции брокера (AML, исправление ошибок, компенсации) — не выдумки. У владельца есть
своя CRM **MICA**; её подключаем позже через API, в этот репозиторий она не въезжает.

## 🔴 Красные линии CRM (не обсуждается)

Помимо общих красных линий (`development-principles` №1–5), у бэк-офиса свои:

1. **Деньги двигаются проводками-корректировками, а не перезаписью баланса.** Не «обнулить», а
   провести «−15000, причина X, оператор Иванов». Тогда любое действие откатывается обратной
   проводкой и видно, откуда взялась сумма. Прямой `SET balance = …` запрещён.
2. **Каждое действие администратора — в журнал** (кто, когда, что, сколько, причина). Это защищает
   владельца: от спора с клиентом, от недобросовестного сотрудника, от вопроса регулятора. Опирайся
   на фундамент журнала событий ([[ADR-003-event-sourcing-and-determinism]]).
3. **Роли и защита.** Денежные операции — за ролью, а не за знанием URL. Первым делом закрой
   `POST /admin/*` — сейчас он **без всякой защиты** (P0-долг в [[backlog]]). Пока он открыт,
   любых денежных операций к нему добавлять нельзя.
4. **Блокировка — обратима и отдельна от списания.** «Разбираемся» = заморозка (не меняет сумму),
   а не списание. Списание — отдельное осознанное действие с причиной.
5. **Никогда не показывай клиенту заведомо ложную картину его денег.** Управлять счётом (блокировать,
   корректировать, замораживать) — да. Рисовать клиенту фальшивую историю сделок/баланс, чтобы
   скрыть действие администратора, — нет. Это обман конкретного человека, а не управление бизнесом.
   Это единственная линия, которая к требованиям владельца не относится и её не просят пересекать —
   но знай её заранее.

## Требования владельца (что CRM должна уметь)

- Полный доступ ко всем аккаунтам и их данным; правка профиля.
- Двигать деньги: пополнить, списать, скорректировать (например, у мошенника с краденым — списать и
  заблокировать; если ошибка и деньги честные — вернуть/начислить). Всё — проводками (см. линию №1).
- Блокировать/разблокировать счёт с мгновенным отзывом сессий (основа есть — сессии удаляются одним
  `DELETE`, [[ADR-018-authentication]]).
- Журнал действий администратора.
- Позже — API под интеграцию с MICA.

## Архитектура (предлагаемая, уточни в своём ADR)

- **Фронт** — новый продукт `apps/crm/` (по [[ADR-017-repo-layout-products]]): свой `Dockerfile`,
  `nginx.conf`, `public/`; общие модули берёшь из `apps/shared/` (i18n, тема). Поддомен через `edge`:
  `crm.meriom.com` (добавь server-блок в `apps/edge/nginx.conf` и запись в hosts/DNS).
- **Бэкенд** — новый модуль `backend/gateway/src/admin.rs` (не размазывай по `lib.rs`), свои роуты
  группой `/admin/*`, за админской ролью. Денежные проводки — через `ledger`/`broker`, добавив им
  метод корректировки с записью в журнал (не прямой мутацией баланса).
- **Роли** — админ-сессия отдельна от клиентской; проверка роли в `authed`-аналоге для админа.
- **Аудит** — таблица в `persistence` (кто/что/когда/сумма/причина), append-only.

Перед первой денежной операцией **напиши ADR** (следующий свободный номер — уточни в `docs/README.md`,
сейчас заняты по ADR-021) с моделью проводок, ролей и аудита. Деньги без design-ADR не трогаем.

## Как не столкнуться с основной сессией

Мы работаем в одном репозитории. Чтобы не клобберить друг друга:

- **Работай в своей ветке** `crm` (не в `master`). Для параллельной работы в той же папке —
  `git worktree add ../Platform-crm crm`, тогда у тебя отдельный рабочий каталог.
- **Владение файлами:** ты трогаешь `apps/crm/`, `apps/edge/nginx.conf` (свой server-блок),
  `backend/gateway/src/admin.rs` и добавляешь методы-корректировки в `ledger`/`broker`/`persistence`.
  **Не переписывай** торговые эндпоинты, auth-ядро, feed, брокерскую торговлю — это зона основной
  сессии; если нужна правка там, согласуй (комментарий в PR).
- **Порты:** одновременно две копии стека не поднимут `443`. Либо стек поднимает кто-то один, либо
  твоя копия идёт под своим `COMPOSE_PROJECT_NAME` и другими портами. Согласуй с владельцем.
- **Мердж — через Pull Request** (CI прогонит тесты/clippy/сборку). Не пуш прямо в `master`.

## Рабочий процесс (как у основной сессии)

- **Design → потом код.** Значимое решение = ADR (`docs/01-architecture/decisions/`); передумали →
  новый ADR, старый `superseded`.
- **Тесты в первую очередь** для всего, что касается денег (проводки, роли, аудит). Бэкенд — через
  `bash scripts/test.sh` (Docker, `rust:slim`), clippy `-D warnings`.
- **Фронт проверяй headless-браузером до слова «готово»** (образ `mcr.microsoft.com/playwright` +
  `playwright-core`), консоль без ошибок. Принцип №20.
- **Новый REST-путь → в регекс прокси** соответствующего `nginx.conf` (граница `(/|$)`, см. BUG-004/007).
- **Док и код едут вместе.** У нового сервиса — свой doc в `docs/02-services/`; баг → `bug-log.md`,
  идея → `backlog.md`.
- **Отчитывайся честно.** Если не проверил — скажи «не проверил». Не выдавай данные за настоящие,
  если они выдуманные. Можно не соглашаться и предлагать своё.
- **Коммиты по-русски**, маленькие, объясняют «зачем»; в конце `Co-Authored-By: Claude Opus 4.8
  <noreply@anthropic.com>`. Секреты — только в `.env` (в git не попадает).

## Первые шаги (чек-лист)

1. Прочитать документы из «Сначала прочитай».
2. Создать ветку `crm` (или worktree).
3. Написать **ADR** по бэк-офису: роли, модель денежных проводок-корректировок, журнал аудита,
   как блокировка отзывает сессии. Согласовать с владельцем.
4. **Закрыть `POST /admin/*`** за админской ролью (P0-долг) — до любых денежных операций.
5. Каркас `apps/crm/` (список клиентов, карточка счёта — только чтение) на существующих данных.
6. Денежные операции — проводками, с тестами и аудитом, по своему ADR.
7. PR → CI зелёный → мердж.
