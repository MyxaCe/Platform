# ADR-016 — Персистентность состояния: PostgreSQL

## Статус

`accepted` (утверждено владельцем 2026-07-20), **реализовано 2026-07-20**.
Черновик `persistence/` от оборванной сессии удалён; крейт написан заново по этому ADR.

### Что отличается от первоначального плана

- **Лок на счёт.** ADR предполагал, что конкурентные мутации одного счёта сериализуются локом
  брокера. Этого мало: запись идёт уже **после** его отпускания, поэтому две операции по одному
  счёту (например, монитор дёрнул SL, пока пользователь закрывал позицию) могли записаться в
  обратном порядке и оставить в БД устаревшее состояние. Добавлен отдельный лок на счёт, который
  держится на всё «мутация → слепок → запись»; разные счета друг друга не ждут. В gateway это
  помощник `with_account`.
- **`closed_deals` ключуются `(user_id, idx)`**, где `idx` — позиция в истории счёта, а не
  `BIGSERIAL`. Так дописывание хвоста идемпотентно и не зависит от длины истории.
- **Демо-сид сделан идемпотентным.** `seed_demo` выполняется на каждом старте и безусловным
  `create` выдавал известному токену НОВЫЙ id: счёт со сделками оставался в базе, но становился
  недоступен. Поймано первой же проверкой рестартом. Теперь `get_or_create`.

## Контекст

Всё изменяемое состояние платформы живёт в оперативной памяти процесса `gateway`:

- счета брокера (баланс, позиции, отложенные ордера, история сделок) — `broker::Broker`;
- реестр пользователей (токен → `UserId`) — `UserRegistry` в `gateway/src/lib.rs`.

Перезапуск контейнера обнуляет всё: пользователи, деньги, открытые позиции, история. Это блокирует
любую дальнейшую работу — плечо, ликвидацию, реальный auth, админский мониторинг делать поверх
исчезающего состояния бессмысленно. Приоритет P0 ([[STATUS]]).

Целевой масштаб (память проекта): **тысячи пользователей + администраторы**, следящие за процессами;
в Фазе 3 — распил на отдельные сервисы; в перспективе — реальные деньги.

### Что было отвергнуто и почему

**Файловые снапшоты (файл на пользователя, atomic-rename).** Первоначальный план; в репозитории
остался нерабочий черновик `persistence/src/lib.rs` от оборванной сессии (не в `members`, не
компилируется, не подключён). Отвергнут: история закрытых сделок растёт неограниченно и лежит в том же
файле → перезапись многомегабайтного файла на каждой сделке; нет запросов для админских отчётов и
проверки инвариантов; несколько процессов Фазы 3 не поделят каталог файлов.

**SQLite.** Отвергнут по двум независимым причинам:

1. **Деньги в проекте — 128-битные целые** (`domain::money::Amount(i128)` по ADR-006,
   `broker::Cents = i128`). Максимальный INTEGER в SQLite — 64 бита. Суммы пришлось бы хранить
   текстом, и по деньгам стало бы невозможно считать в SQL: ни `SUM(balance)` для проверки
   инварианта (красная линия №5), ни `WHERE balance < 0`, ни отчёты для админов. База есть — пользы
   от неё на главном типе данных нет.
2. SQLite — файл одного процесса. Распил на сервисы (Фаза 3) потребовал бы его выкинуть, то есть
   переписать персистентность второй раз.

## Решение

**PostgreSQL** как durable-хранилище состояния, за трейтом `Persistence` в крейте `persistence`.
Существующий черновик `persistence/src/lib.rs` **удаляется и пишется заново** по этому ADR.

### Роли: память — рабочее состояние, БД — источник восстановления

Брокер остаётся **in-memory** и остаётся чистой синхронной логикой без I/O — иначе нарушается
принцип №6 (доменное ядро не знает про БД) и тик монитора превратился бы в чтение всех позиций всех
пользователей из БД каждые 500 мс.

БД — durable-проекция этого состояния:

- **на старте** `gateway` читает БД и наполняет `Broker` и `UserRegistry`;
- **при каждой мутации** адаптер (gateway) записывает изменение в БД.

SQL живёт только в крейте `persistence`; ни `broker`, ни `domain` о нём не знают.

### Порядок записи и откат

Мутация выполняется под уже существующим `Mutex<Broker>`, но **fsync/сеть под локом недопустимы** —
это заблокировало бы торговлю всех пользователей. Порядок:

1. под локом мутировать брокер и снять слепок затронутого счёта;
2. **отпустить лок**;
3. записать слепок в БД одной транзакцией;
4. если транзакция не прошла — вернуть счёт к предыдущему слепку (под локом) и ответить `503`.

Откат корректен, потому что слепок одного счёта мал, а конкурентные мутации того же счёта
сериализуются тем же локом.

### Долговечность

- **Действия пользователя** (`open`, `close`, `place_pending`, `cancel_pending`, создание
  пользователя, депозит): ответ API отправляется **после коммита** транзакции. Клиент увидел `200`
  → данные на диске. Потерь нет.
- **Сработавшие триггеры** (SL/TP и лимитные ордера из фонового монитора): одна транзакция на тик,
  все затронутые счета вместе. Потеря при падении — максимум последний тик (~500 мс); после
  перезапуска нетронутые триггеры сработают снова по актуальным ценам.

### Изменение API брокера

`Broker::check()` сейчас возвращает `()`, прогоняя все счета — непонятно, кого сохранять. Наивное
«сохранить всех после тика» = тысячи записей дважды в секунду. Сигнатура меняется:

```rust
/// Прогнать триггеры; вернуть id счетов, состояние которых изменилось.
pub fn check(&mut self, marks: &HashMap<u32, i64>) -> Vec<UserId>;
```

Пустой результат (обычный случай — цена движется, но ничего не сработало) означает: писать нечего.

### Схема

Деньги — `NUMERIC(38,0)`: вмещает весь диапазон `i128` и остаётся полноценным числом для SQL.

```sql
CREATE TABLE users (
  id          BIGINT PRIMARY KEY,
  token       TEXT NOT NULL UNIQUE,     -- dev-токены; хэши паролей — при настоящем auth
  created_at  TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE TABLE accounts (
  user_id     BIGINT PRIMARY KEY REFERENCES users(id) ON DELETE CASCADE,
  balance     NUMERIC(38,0) NOT NULL,
  next_id     BIGINT NOT NULL           -- счётчик id позиций/ордеров счёта
);

CREATE TABLE positions (
  user_id     BIGINT NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  id          BIGINT NOT NULL,          -- id в пределах счёта
  instrument  INTEGER NOT NULL,
  side        SMALLINT NOT NULL,        -- 0 = Long, 1 = Short
  qty         BIGINT NOT NULL,
  entry       BIGINT NOT NULL,
  pd          SMALLINT NOT NULL,
  qd          SMALLINT NOT NULL,
  margin      NUMERIC(38,0) NOT NULL,
  sl          BIGINT,
  tp          BIGINT,
  PRIMARY KEY (user_id, id)
);

CREATE TABLE pendings (            -- те же поля, price вместо entry/margin
  user_id     BIGINT NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  id          BIGINT NOT NULL,
  instrument  INTEGER NOT NULL,
  side        SMALLINT NOT NULL,
  qty         BIGINT NOT NULL,
  price       BIGINT NOT NULL,
  pd          SMALLINT NOT NULL,
  qd          SMALLINT NOT NULL,
  sl          BIGINT,
  tp          BIGINT,
  PRIMARY KEY (user_id, id)
);

CREATE TABLE closed_deals (
  seq         BIGSERIAL PRIMARY KEY,    -- глобальный порядок; append-only
  user_id     BIGINT NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  instrument  INTEGER NOT NULL,
  side        SMALLINT NOT NULL,
  qty         BIGINT NOT NULL,
  entry       BIGINT NOT NULL,
  exit        BIGINT NOT NULL,
  pnl         NUMERIC(38,0) NOT NULL,
  pd          SMALLINT NOT NULL,
  qd          SMALLINT NOT NULL,
  closed_at   TIMESTAMPTZ NOT NULL DEFAULT now()
);
CREATE INDEX closed_deals_user_idx ON closed_deals (user_id, seq DESC);
```

`positions` и `pendings` для затронутого счёта переписываются в транзакции целиком (`DELETE` +
`INSERT`) — их единицы-десятки. `closed_deals` **только дописывается**: стоимость закрытия сделки не
зависит от длины истории.

### Драйвер и типы

`sqlx` (async, пул соединений, работает с tokio). Запросы — runtime-проверяемые (`query`/`query_as`),
**без макросов `query!`**: макросы требуют живую БД на этапе компиляции, что сломало бы сборку
образа в Docker.

`i128` ↔ `NUMERIC` не маппится напрямую: `sqlx` отдаёт `NUMERIC` как `BigDecimal`. В `persistence`
пишутся две функции преобразования с проверкой диапазона и нулевой дробной части; при нарушении —
ошибка, а не молчаливое округление (красная линия №1). Это цена хранения денег честными числами;
альтернатива (текст) отнимала бы SQL-арифметику.

### Инварианты (красная линия №5)

Наличие SQL позволяет закрыть техдолг по принципу №5 отдельной проверкой:

```sql
SELECT count(*) FROM accounts WHERE balance < 0;
```

Проверка вызывается на старте после загрузки; расширяется вместе с плечом и ликвидацией.

### Инфраструктура

- `docker-compose.yml`: сервис `postgres:16-alpine`, том `pgdata`, `depends_on` + healthcheck у
  `gateway`.
- Схема применяется на старте `gateway` идемпотентным DDL (`CREATE TABLE IF NOT EXISTS`) из
  `persistence`. Полноценные версионируемые миграции — при первом изменении схемы на живых данных.
- Строка подключения — `DATABASE_URL`. Если переменная не задана, `gateway` поднимается с
  `NoopStore` (всё в памяти, как сейчас) — так сохраняются существующие тесты и локальный запуск
  без БД.
- `scripts/test.sh` поднимает временный контейнер Postgres для интеграционных тестов
  `persistence`; юнит-тесты `broker`/`core`/`ledger` БД не требуют.

## Последствия

**Плюсы**

- Перезапуск больше не теряет пользователей, деньги, позиции и историю.
- Админские отчёты и проверки инвариантов — обычные SQL-запросы по настоящим числам.
- Хранилище переживает Фазу 3: несколько сервисов работают с одной БД; появляются бэкапы,
  репликация, восстановление на момент времени — необходимое условие перед реальными деньгами.
- История сделок не удорожает запись.

**Минусы и риски**

- Новая инфраструктурная зависимость: контейнер БД, пул соединений, живая БД для части тестов.
- Конверсия `i128` ↔ `BigDecimal` на каждой денежной записи — лишний слой, требующий тестов на
  граничные значения.
- Состояние существует в двух местах (память + БД). Расхождение возможно при падении между
  мутацией и коммитом; смягчается откатом слепка, но полностью снимается только событийной моделью
  Фазы 3.
- **Брокер по-прежнему не событизирован** — действующее исключение из красной линии №3
  ([[development-principles]]). Этот ADR даёт долговечность, но **не** даёт аудируемость: по БД
  видно текущее состояние, а не доказуемая история его получения. Снимается в Фазе 3.
