# ADR-023 — Интеграция терминала как White Label-страницы платформы

## Статус

`accepted` (2026-07-25). Развивает [[ADR-022-standalone-terminal-pivot]]: отвечает на его открытый
вопрос «как внешний сайт/CMS авторизует пользователя в терминале». Терминал — **ведомый**: он
подстраивается под событийную архитектуру платформы, а не наоборот (решение владельца).

## Контекст

После пивота терминал — автономная встраиваемая торговая страница. Платформа (отдельный продукт с
CMS) хочет поставлять её на N страновых сайтов: одна страница, бренд каждого сайта — из CMS,
пользователь приходит из кабинета сайта. Согласование прошло перепиской (файлы `Ответы команде
терминала.md`, `Интеграция с терминалом*.md`) и передачей контракт-пакетов (`theming-pack/`,
`sso-pack/`).

## Решения

**Поставка** — `iframe` (не JS-виджет: приложение владеет своим origin). `frame-ancestors` со
списком доменов сайтов — конфигурируемый env, список даёт платформа.

**Тенант** — один инстанс на все бренды, тенант per-request. Ключ — `?site=` (slug
`^[a-z0-9-]{2,32}$`, напр. `apex-ru`), **обязателен всегда** (и на публичной странице до логина). В
авторизованном режиме `token.tenant` обязан совпадать с `?site=`, иначе `403` (защита от подмены).

**Темизация (фаза Т1 — СДЕЛАНО)** — принят theming-пакет платформы: `tokens.v1.css` (дизайн-токены
RGB-каналами, обе темы через `data-theme`) + `GET /v1/cms/brand` (имя, логотип, `primaryColor`).
Адаптер на стороне терминала (`apps/terminal/public/theming.js` + мост в `style.css`):
- платформенные токены — единственный источник цвета; семантические переменные терминала
  (`--bg/--panel/--up/--down/--brand`) построены поверх них. Коллизия имён `--accent`
  (у платформы это каналы, у нас был цвет) снята переименованием нашего цвета в `--brand`;
- загрузчик бренда: fetch → валидация по `cms.brand.schema.json` → применение `--accent`
  (hex→каналы), логотип, имя; **last-good** кэш; refresh 5 мин; без CMS — палитра платформы
  («не раскрашиваться мусором»). **CMS-ключ в браузер не кладём** (замечание платформы): brand
  запрашивается через их gateway-прокси, ключ у него server-side; тенант — из `?site=`;
- тёмная/светлая темы через `data-theme`, приём `?theme=`, кнопка-переключатель; график
  (Lightweight Charts) перечитывает цвета из токенов на смене темы/бренда;
- `--on-accent` вычисляется по яркости бренд-цвета (читаемый текст на кнопках).

**SSO (фаза Т2 — РЕАЛИЗОВАНО, ждёт e2e с реальным токеном)** — короткоживущий **handoff-JWT**
(RS256, `kid: platform-sso-1`), выпускает Auth-сервис платформы; сессии платформы остаются
opaque+revocable. Терминал: валидирует токен по JWKS (только `RS256`; `iss=platform-auth`,
`aud=terminal`, `exp` ±30с, one-shot `jti`, `tenant==?site=`), затем чеканит **свою** сессию
TTL ≤ 15 мин. **Сессия — bearer в памяти iframe, не cookie** (в iframe это third-party cookie,
их режут браузеры). Доставка — `postMessage` (`sso.token` / `token.refresh.request` /
`sso.logout`) с проверкой `event.origin`. Единый логаут: погашенная сессия не переотдаёт токен ⇒
разлогин ≤ TTL, `sso.logout` делает мгновенным. Счёт — по ключу `(tenant, sub)`, персистентно.

Реализация: gateway `sso.rs` (валидатор JWKS+RS256, стор сессий, one-shot jti), `/v1/session`
(+`/logout`), торговые ручки требуют bearer при включённом SSO (dev-тумблер `SSO_DISABLED`, чтобы
стек/тесты жили на счёте по умолчанию); `identities(tenant,sub)→user_id` в PostgreSQL; фронт
`sso.js` (postMessage, bearer в памяти) + `Authorization` в `api.js`. Проверено: юнит-тесты против
**реального ключа платформы** (подпись сходится, exp/мусор отклоняются), и `/v1/session` в живом
стеке валидирует против **живого JWKS** кабинета (:3002) — мусорный токен → 401. Полный успешный
handoff (реальный свежий токен → сессия → сделка от лица пользователя) остаётся за e2e-прогоном
через кабинет.

**Демо-счёт (фаза Т3)** — синхронного чтения нет. Терминал владеет торговым состоянием и
**публикует события** в конверте v1 (`terminal.account.opened/trade.executed/position.closed/
balance.changed`) через transactional outbox (ложится в существующую транзакцию `with_account`,
ADR-016). Кабинет/CRM строят проекции. Публикуем изменения состояния, **не** нереализованный P&L по
тикам (затопит шину) — живое equity считается на стороне потребителя. Шина — RabbitMQ,
topic-exchange `platform.events`, дедуп по `event_id`. Стартовый баланс — из конфига сайта в CMS.

**Инструменты** — allow-list per-tenant из CMS (регуляторика: уважать и в данных, и в торговле).
Маппинг на числовой `instrument id` терминала (поле `terminalInstrumentId`). Источник котировок
позже переедет с прямого Binance на общий **MDS** (ADR-024 платформы) — тогда снимется и
символ-маппинг, и подписка по символам решится на их fan-out.

**Версионирование** — `/v1`-префикс + общий `platform-contracts` как условие старта интеграции.

## Последствия

- Т1 (бренд) работает и проверен headless; терминал красится из CMS в рантайме, обе темы, без CMS
  деградирует на палитру платформы. Не ждёт больше ничего.
- Т2/Т3 гейтятся внешними зависимостями платформы (Auth-сервис + JWKS/эндпоинты, CMS `sites`,
  шина + референс relay, решение по ключу счёта). Реализацию начинаем по мере их появления.
- SSO возвращает авторизацию в терминал, но в правильной форме (handoff, без паролей/пасскеев) —
  ровно то, что снял ADR-022. Крейт `auth` и модули входа не воскрешаются; нужен лишь
  JWT/JWKS-валидатор + сессия.
- **R-T1 (breadth):** терминал сегодня только крипта (топ-30 Binance); форекс/акции/сырьё
  невозможны без платного провайдера — отдельный трек MDS, не обещать сайтам в первой фазе.
