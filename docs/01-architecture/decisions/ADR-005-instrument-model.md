# ADR-005 — Модель инструмента и мульти-инструментный матчинг

## Статус

`accepted`.

## Контекст

Ядро Фазы 1 матчило одну абстрактную книгу без понятия торговой пары. Реальной бирже нужны
инструменты (BTC-USDT и т.д.) со своими параметрами: точность, шаг цены, шаг объёма, минимум.
От этого зависят валидация заявок, маршрутизация по книгам и будущий Ledger (какие активы двигать).

## Решение

Вводим **инструмент** и **реестр инструментов**.

- `Instrument { id, symbol, base, quote, price_decimals, qty_decimals, tick_size, lot_size, min_qty }`.
  `base`/`quote` (`AssetId`) пока просто данные — понадобятся Ledger'у в Фазе 2.
- `InstrumentRegistry` — конфиг-состояние движка; инструмент регистрируется до торгов, тогда же
  создаётся его пустая книга.
- Движок хранит **по одной книге на инструмент** (`HashMap<InstrumentId, OrderBook>`) и маршрутизирует
  команды по `instrument`.

**Решение А — команды несут `instrument`.** И `PlaceOrder`, и `CancelOrder` содержат `InstrumentId`.
Так отмена не требует глобального индекса `OrderId -> Instrument` в движке (меньше состояния = меньше
багов рассинхронизации). Шлюз знает символ отменяемой заявки — это реалистично.

**Решение Б — каждое событие несёт `instrument`.** В событийной модели журнал — глобальный и
чересполосный; каждое событие обязано быть самодостаточным, чтобы проекция (напр. market data по
символу) могла фильтровать без опоры на контекст батча.

**Валидация при размещении** (порядок и причины отказа):
`UnknownInstrument` → `NonPositiveQty` → `QtyNotOnLot` → `BelowMinQty` →
(для лимитной) `NonPositivePrice` → `PriceNotOnTick`.

## Последствия

- `Command` и `Event` получают поле `instrument` (ломающее изменение сигнатур; тесты обновлены).
- Приоритетные счётчики `seq`/`trade_id` остаются глобальными и монотонными — детерминизм сохранён,
  id сделок глобально уникальны.
- Пока нет полноценного реестра активов (`AssetId` — опаковый id). См. [[backlog]].
- Параметры инструмента валидируются при регистрации (tick/lot/min > 0).
