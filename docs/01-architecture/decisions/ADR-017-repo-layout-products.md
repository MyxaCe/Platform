# ADR-017 — Структура репозитория: продукты отдельно от ядра

## Статус

`accepted` (2026-07-21).

## Контекст

До сих пор в репозитории было ровно два «жителя»: Rust-крейты лежали россыпью в корне, а весь
браузерный код — в единственном каталоге `web/`. Пока продукт был один (торговый терминал), это
работало.

Теперь продуктов планируется **четыре**:

1. **Сайт брокера** — публичная витрина, привлечение и регистрация клиентов;
2. **Торговый терминал** — то, что уже сделано;
3. **Личный кабинет клиента** — документы, верификация, пополнение/вывод, история;
4. **CRM** — у владельца уже есть своя, **MICA**; подключается позже, в этом репозитории не живёт.

Складывать страницы сайта в ту же папку статики, что и терминал, нельзя: у них разный жизненный
цикл, разный деплой и ноль общего кода. Владелец сформулировал прямо — «начинаю путаться и не
понимаю, где что».

## Решение

**Продукты — в `apps/`, ядро платформы — в `backend/`.** Каждый продукт собирается своим образом и
поднимается своим контейнером.

```
backend/            Rust-workspace: ядро и сервер
  Cargo.toml        domain, core (matching), ledger, orchestrator,
  domain/ core/ …   marketdata, broker, persistence, gateway
apps/
  terminal/         Торговый терминал (Dockerfile + nginx.conf + public/)
  site/             Сайт брокера
  cabinet/          Личный кабинет — появится позже
docs/  scripts/  docker-compose.yml
```

Правила:

- **У каждого продукта в `apps/` свои `Dockerfile`, `nginx.conf` и `public/`.** Общий код между
  продуктами не заводим до тех пор, пока не появится реальное дублирование; тогда — отдельный
  каталог общих модулей по контракту [[ADR-015-reusable-frontend-modules]] (виджеты уже
  самодостаточны и возят свою CSS, поэтому переносятся копированием файла).
- **Ядро не знает про продукты.** `backend/` собирается и тестируется само по себе
  (`scripts/test.sh` монтирует именно `backend/`).
- **Порты наружу разные:** терминал `8888`, сайт `8889` (диапазон 8080–8282 занят WinNAT на
  dev-машине). У каждого своего продукта — свой контейнер, падение одного не роняет остальные.
- **CRM (MICA) в репозиторий не въезжает** — интеграция будет через API шлюза, отдельным решением.

## Последствия

- **Плюсы:** видно, где что лежит; сайт и терминал деплоятся независимо; новый продукт добавляется
  созданием каталога в `apps/` и сервиса в compose, ничего не задевая. Совпадает с принципом
  «модульные границы = будущие границы сервисов» ([[development-principles]] №10).
- **Минусы/плата:** пути в сборке стали длиннее (`context: ./backend`, `context: ./apps/terminal`);
  один раз пришлось поправить `scripts/*.sh`, `docker-compose.yml` и ссылки в документации.
- **История git сохранена** — перенос сделан через `git mv`.
- Замена одного `web`-контейнера на `terminal` + `site` означает новые имена контейнеров
  (`exchange-terminal`, `exchange-site`); при обновлении на живой машине нужен
  `docker compose down --remove-orphans`, иначе останется висеть старый `exchange-web`.
